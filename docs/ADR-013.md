# ADR-013 — `vendors` 마스터는 공유 풀, 공유는 `vendor_access_grants` 승인제

**상태**: Proposed
**날짜**: 2026-05-13
**관련**: ADR-012, ADR-004 (멀티테넌트), CLAUDE.md (P-4, P-5, P-7)

---

## 배경

ADR-012로 국내 농가 마스터 `vendors` 테이블을 신설했다. 다음 질문이 남는다:

> **농가 정보는 회사별 자산인가, 공유 자산인가?**

세 시나리오가 충돌한다:

1. **회사별 완전 격리** — 형이 모은 1,800건 농가 정보를 강의생이 못 봄. 매번 새로 모아야 함. 강의생 확장 비전(CPS Phase 3) 좌절.
2. **모두 공유** — 가입자 누구나 모든 회사의 농가 풀 조회. **개인정보(`rpersBirthdt`, `rpersGender`) 누출 위험** + 형이 모은 자산 무료 배포.
3. **승인제** — 풀 소유자(`grantor_company_id`)가 신청자(`grantee_company_id`)에게 명시적 승인. 강의생 확장 가능 + 자산 통제 가능.

또한 통화 기록(`vendor_call_logs`)과 후보 결정(`product_vendor_candidates`)은 **각 회사의 영업 자산**이라 공유 대상이 아니다.

## 결정

### D-1. `vendor_access_grants` 테이블 신설

```sql
CREATE TABLE vendor_access_grants (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  grantor_company_id uuid NOT NULL REFERENCES companies(id),  -- 풀 소유자 (예: BUYWISE.CO)
  grantee_company_id uuid NOT NULL REFERENCES companies(id),  -- 신청자 (예: 강의생 A)
  status text NOT NULL DEFAULT 'pending',
    -- 'pending' | 'approved' | 'rejected' | 'revoked'
  requested_at timestamptz NOT NULL DEFAULT now(),
  decided_at timestamptz,
  decided_by_user_id uuid REFERENCES users(id),
  reason text,           -- 신청 사유 (강의생 → 형)
  notes text,            -- 형의 승인/거절 메모
  UNIQUE (grantor_company_id, grantee_company_id)
);
```

### D-2. `vendors` 의 RLS 정책 (공유 SELECT)

```sql
ALTER TABLE vendors ENABLE ROW LEVEL SECURITY;

-- SELECT: 본인 회사 + 승인받은 grantor 회사
CREATE POLICY "vendors_select_own_or_granted" ON vendors
  FOR SELECT TO authenticated
  USING (
    company_id = current_company_id()
    OR company_id IN (
      SELECT grantor_company_id FROM vendor_access_grants
      WHERE grantee_company_id = current_company_id()
        AND status = 'approved'
    )
  );

-- INSERT/UPDATE/DELETE: 본인 회사만
CREATE POLICY "vendors_modify_own" ON vendors
  FOR ALL TO authenticated
  USING (company_id = current_company_id())
  WITH CHECK (company_id = current_company_id());
```

### D-3. `vendor_call_logs`, `product_vendor_candidates` 는 완전 격리

- 두 테이블 모두 SELECT/INSERT/UPDATE/DELETE 정책 = `company_id = current_company_id()` 만 허용
- 공유 풀로 농가는 보더라도, **다른 회사가 그 농가와 통화한 내용/후보 결정은 보이지 않음**
- 영업 비밀 보호 + 신뢰도 마킹(P-3) 일관성

### D-4. 개인정보 컬럼 RLS 강화

`vendors` 테이블의 일부 컬럼은 **승인받았어도 개인정보** 보호:
- `rpersBirthdt` (생년월일)
- `rpersGender` (성별)

이 두 컬럼은 **풀 소유자만 조회 가능**. 승인받은 grantee 는 NULL 로 반환.

구현: View 또는 컬럼 단위 정책 (Postgres 15+ 가능).

```sql
CREATE OR REPLACE VIEW vendors_for_grantee AS
SELECT
  id, company_id, bizName, bizOwnerName, reprTelNo, bizMobile, bizAddress, bizNo,
  -- 개인정보는 NULL 마스킹
  CASE WHEN company_id = current_company_id() THEN rpersBirthdt ELSE NULL END AS rpersBirthdt,
  CASE WHEN company_id = current_company_id() THEN rpersGender ELSE NULL END AS rpersGender,
  bizSector, bizType, source_site, also_listed_on, intro_html, created_at
FROM vendors;
```

(또는 애플리케이션 레이어에서 마스킹 — Phase B 4번 PR에서 결정)

### D-5. 승인제 운영 UX

화면 `/vendors/access` (4번 PR):

```
[받은 요청]                              [내가 보낸 요청]
강의생 김OO — 농가 풀 조회 신청          형 → 강의생 박OO 풀 (승인됨)
  사유: "참외 농가 공부하고 싶어요"        기간: 무제한
  [✅ 승인] [❌ 거절]                      [🚫 회수]

[활성 승인 중]
- 강의생 김OO (참외 농가 접근, 2026-04-15 부터)
- 강의생 이OO (전체 농가, 2026-04-20 부터)
```

승인 후 grantee 가 `/vendors` 들어가면 자기 회사 + grantor 회사 농가 모두 검색됨.

### D-6. 1번 PR 에서는 스키마만, RLS+UI 는 4번 PR

1번 PR 범위에서 `vendor_access_grants` 는 **테이블만 생성**. RLS 정책과 `/vendors/access` UI 는 **4번 PR**.

이유:
- 1번 PR 범위 폭증 방지 (마이그레이션 + 임포트 통로 + 검색 페이지로 이미 큰 작업)
- 4번 PR에서 RLS + UI + 알림(승인 요청 알림) 묶어서 일관성 있게 구현

1번 PR 의 `vendors` RLS = **회사 격리만** (`company_id = current_company_id()`). 공유 SELECT 는 4번 PR에서 추가.

## 이유

### 승인제가 완전 격리/완전 공유보다 나은 이유

1. **자산 통제** — 형이 1,800건 모은 노력이 무료로 배포되지 않음
2. **점진적 확장** — 강의생이 처음엔 자기 풀만, 졸업/심화 과정에서 형 풀 접근 권한 받음
3. **법적 안전** — 농가 동의 없이 개인정보 광역 공유 안 함 (개인정보보호법)
4. **신뢰 신호** — "X명에게 풀 공유 중" = 형의 명성 시그널

### 통화/후보 격리가 강제인 이유 (P-5)

1. **영업 비밀** — "형이 어느 농가에 어떤 가격 제시했는지" 가 새 나가면 협상력 잃음
2. **신뢰도 마킹 일관성(P-3)** — 다른 회사의 ✅ confirmed 가 내 회사에서도 confirmed 처럼 보이면 오인 위험
3. **단순성** — `vendor_call_logs` 의 RLS 가 단순(자기 회사만) → 디버깅 쉬움

### 개인정보 추가 마스킹 이유 (P-7)

1. **법적 의무** — 생년월일/성별은 개인정보보호법상 민감 정보
2. **농가 보호** — 형이 통화로 알게 된 정보를 강의생이 그대로 보면 농가 동의 없는 정보 이전
3. **신뢰 유지** — 농가에게 "이 정보는 BUYWISE에서만 봅니다" 약속 지킴

### 1번 PR 분리 이유

1. **PR 무게 균형** — 1번 PR 이미 크다 (5개 테이블 + 임포트 + 검색)
2. **테스트 격리** — RLS + UI 동시 테스트는 4번 PR에서 한 번에 검증
3. **헌법 §3 (하니스 워크플로우)** — 작은 PR + 자기검증 5+1 원칙

## 대안 검토

### 대안 A: 완전 격리 (회사별 vendors 풀)

- 모든 가입자가 자기 농가만 관리
- 장점: RLS 단순, 개인정보 위험 없음
- 단점:
  - 강의생이 매번 새로 농가 모아야 함 (확장 비전 좌절)
  - 같은 농가(예: 안동 사과 농가)가 회사마다 중복 저장 → 데이터 중복
  - **기각**: CPS Phase 3 위반

### 대안 B: 완전 공유 (모든 vendors 광역 SELECT)

- 가입자 누구나 모든 회사 농가 조회
- 장점: 데이터 풍부도 최대, 구현 단순
- 단점:
  - 개인정보 광역 공유 (법적 위험)
  - 형 자산 무료 배포 (비즈니스 의도 X)
  - **기각**: P-7 위반

### 대안 C: 풀별 라이센스 결제

- 풀 소유자가 가격 설정, grantee가 결제 후 접근
- 장점: 수익화 가능
- 단점:
  - SaaS 결제 시스템 추가 필요 (Phase 3 이후)
  - 강의생-스승 관계엔 부담
  - **보류**: Phase 4 이후 검토. 현 단계는 무료 승인제로 시작

### 대안 D: 시간 제한 승인

- `vendor_access_grants.expires_at` 컬럼 추가, 자동 회수
- 장점: 강의생 졸업 후 자동 차단
- 단점:
  - 첫 구현 복잡도 증가
  - 형이 수동 회수해도 충분
  - **보류**: 4번 PR 끝나면 운영하면서 결정. 필요 시 ADR-014 로 추가

## 위반 시 (즉시 불합격)

- ❌ `vendors` 의 SELECT 정책에 `grantor_company_id` 조건 누락 (광역 공유 = P-5 위반)
- ❌ `vendor_call_logs`, `product_vendor_candidates` 가 공유 SELECT 허용 (영업 비밀 누출)
- ❌ `rpersBirthdt`, `rpersGender` 가 grantee 회사에 NULL 마스킹 없이 노출 (P-7 위반)
- ❌ 1번 PR 에서 `vendor_access_grants` RLS 정책까지 적용 (PR 분리 위반)
- ❌ 승인 없이 강의생이 형 농가 풀 조회 가능 (D-2 위반)
