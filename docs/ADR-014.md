# ADR-014 — 크롤링은 "셀렉터 레지스트리 + 계약 + 자격증명 금고" 위에서만 한다

**상태**: Proposed
**날짜**: 2026-08-14
**관련**: CLAUDE.md (P-1 빈 결과 은폐 금지, P-2 실패 시 명시 에러, P-3 신뢰도 마킹, P-7 시크릿 노출 금지), ADR-001 (Vercel), ADR-008 (쿠팡 진입 난이도)
**참조 구현**: `market-research-toolkit` (Python) 의 `registry/` · `sources/base.py` · `report/`

---

## 배경

우리는 외부 사이트에서 데이터를 긁어 그 위에 사업 판단을 올린다. 셀록홈즈·아이템스카우트는
공개 API 가 아니라 **웹사이트 내부 API 와 화면**이다. 그쪽이 예고 없이 바뀌는 것은 사고가
아니라 정상이다. 문제는 바뀌었을 때 **우리가 그 사실을 알 수 있느냐**다.

작업 전 코드에는 이런 자리가 있었다.

| 위치 | 무슨 일이 일어나는가 |
|---|---|
| `src/lib/sello-scraper/run-scrape.ts` (수집 대기 루프 뒤) | 대기 시간이 다 되면 그대로 진행해 **0행이어도 `ok: true`** 로 저장. 워커는 '완료'로 기록 |
| `scripts/sello-scraper/scrape.ts` | `run-scrape.ts` 와 **같은 파서가 복제**돼 이미 서로 어긋남. 둘 다 `page.evaluate` 문자열 안이라 타입 검사도 테스트도 못 받음 |
| `run-scrape.ts` 의 `'선택'` / `'1 페이지 상품분석'` 클릭 | 반환값을 확인하지 않아 **못 눌러도 조용히 진행** → 엉뚱한 범위 수집 |
| `src/lib/itemscout/client.ts` (`subcategories`, `category/{id}/data`, `keyword/trend`) | 응답 모양이 달라도 **`return []`** → "결과 없음"과 "구조 변경"이 화면에서 동일 |
| `src/lib/sellochomes/client.ts` (chart) | `results` 가 없으면 `[]` → 라우트가 `ok: true, analysis: null` 로 200 응답 |
| `src/lib/sellochomes/client.ts` (페이지네이션) | 빈 페이지가 나오면 조용히 멈추고 **"전부 수집" 처럼 배열만** 반환 |
| `src/lib/sellochomes/keyword-pool.ts` | 풀 파일 파싱 실패 → `[]` → 워커가 **아무것도 안 하고 성공** |
| `src/lib/itemscout/client.ts` (토큰) | 메모리·파일뿐 → Vercel 인스턴스마다 따로 놀아 설정 화면에서 저장해도 다른 인스턴스는 못 봄 |
| `src/lib/sellochomes/client.ts` (fetch) | 같은 사이트를 부르는 fetch 블록이 **5군데**, User-Agent 가 Chrome 147/149 로 서로 다름 |

이 전부가 하나의 원인에서 나온다: **"맞는 결과"가 무엇인지 코드가 선언한 적이 없다.**
선언이 없으니 판정이 없고, 판정이 없으니 실패가 성공과 구분되지 않는다.

## 결정

### D-1. 셀렉터는 코드가 아니라 데이터다 — `src/lib/crawl/selectors.json`

모든 DOM 셀렉터와 외부 API 응답 경로를 한 파일로 외부화한다. 각 항목은 다음을 갖는다.

```jsonc
"sello.row": {
  "kind": "css",                       // 'css' | 'json'
  "primary": "ul.td[data-rank]",       // 지금 쓰는 셀렉터
  "fallbacks": ["ul[data-rank]"],      // 깨졌을 때 순서대로 시도
  "contract": {                        // ★ "맞다"의 정의
    "minMatches": 10,
    "attr": "data-rank",
    "mustMatch": "^\\d+$"
  },
  "within": null,                      // 다른 셀렉터 안쪽 기준이면 그 id
  "description": "…",                  // 사람이 읽을 설명
  "requiresBrowser": true,
  "healedAt": null, "healedFrom": null
}
```

`contract` 가 이 ADR 의 핵심이다. 이게 없으면 자동 치유가 성립하지 않는다 —
어떤 후보를 채택해도 되는지 판단할 근거가 없기 때문이다.

- CSS 계약: `minMatches` / `attr` / `mustMatch` / `minTextLen`
- JSON 계약: `status` / `jsonKeys` (`data.items` 같은 점 표기 경로)

**계약 스키마는 `kind` 로 갈라 엄격(strict)하게 검증한다.** 느슨하게 두면 JSON 계약이
CSS 스키마에 먼저 매치돼 `status`·`jsonKeys` 가 조용히 깎여 나가고, 그러면 모든 응답
계약이 빈 계약이 되어 아무것도 검증하지 못한다. (실제로 구현 중 이 버그가 났고
`src/lib/crawl/registry.test.ts` 에 회귀 테스트로 고정했다.)

### D-2. 계약을 통과하지 못한 결과는 성공이 아니다

- DOM: 수집을 마치기 전 `checkSelectorOnPage(page, 'sello.row')` 로 확인한다.
  못 지키면 치유를 한 번 시도하고, 그래도 안 되면 `{ ok: false, reason: 'contract' }` 를 돌려준다.
  API 라우트는 이걸 **502** 로 옮긴다 — 재시도로 풀리는 문제가 아니라 사람이 손봐야 하는 문제이기 때문이다.
- JSON: `crawlFetchJson({ contractId })` 가 응답 직후 계약을 검사하고, 어긋나면
  `CrawlError('schema_mismatch')` 를 던진다.
- 조용한 `return []` 는 전부 제거했다. 단, **"아직 준비 안 됨"이 정상 상태인 곳**
  (`keyword-caching` 폴링, itemscout `data.data === null`) 은 그대로 `null`/`[]` 을 유지하되
  주석으로 그 이유를 남긴다.

### D-3. 깨지면 4단계로 스스로 고쳐 본다 (`src/lib/crawl/heal.ts`)

```
1) primary        계약 통과 → 종료
2) fallbacks      순서대로 시도, 통과하면 승격
3) 휴리스틱 역추출  계약이 정의한 "정답 노드"를 먼저 찾고,
                  난수 클래스(sc-*, css-*, jsx-*, CamelCase 조각이 1~2글자)는 버리고
                  data-testid·role·itemprop·aria-label·안정 클래스로 셀렉터를 재조립.
                  만든 후보를 같은 문서에 다시 적용해 계약으로 검증
4) 스냅샷 내보내기  전부 실패 → data/crawl-snapshots/ 에 page.html + PROMPT.md.
                  레지스트리는 손대지 않는다
```

**어느 단계에서 나온 후보든 계약 검증을 통과해야만 승격된다.** Claude 가 준 후보도
예외가 아니다 — `npm run crawl:adopt` 은 저장된 스냅샷으로 재검증한 뒤 통과한 것만 채택한다.
틀린 답을 받아도 레지스트리는 오염되지 않는다.

모든 변경은 `data/crawl-registry/history.jsonl` 에 남고 `npm run crawl:revert` 로 되돌린다.

### D-4. 파싱은 브라우저가 아니라 Node 에서 한다 (cheerio)

브라우저는 `page.content()` 로 **HTML 문자열만** 내주고, 계약 검증·역추출·표 추출은
전부 `src/lib/crawl/dom.ts` 에서 한다.

이유는 이 저장소가 이미 밟고 기록해 둔 함정이다 (`scripts/sello-scraper/scrape.ts:62`):
tsx/esbuild 가 함수에 `__name()` 래퍼를 넣는데 브라우저 페이지에는 `__name` 이 없어
ReferenceError 가 난다. 그래서 기존 코드는 파싱 로직을 전부 문자열로 적었고, 그 결과
타입 검사도 테스트도 못 받았다.

Node 로 옮기면서 얻은 것:
- `__name` 함정이 구조적으로 사라짐
- 픽스처 HTML 만 있으면 **브라우저 없이 단위 테스트** (`src/lib/crawl/dom.test.ts`)
- 저장된 스냅샷 재검증도 브라우저 불필요
- 폴링과 최종 파싱이 **같은 추출 결과**를 봄 (예전엔 서로 다른 `page.evaluate` 라 갈릴 수 있었다)

의존성으로 `cheerio` 를 추가한다. jsdom 보다 가볍고 CSS 셀렉터 지원이 우리 용도에 충분하다.

### D-5. 자격증명은 하나의 금고를 지난다 (`src/lib/crawl/vault.ts`)

우선순위: **메모리(TTL 30초) → DB `system_settings` → 파일 `.data/` → 환경변수**

셀록홈즈 쿠키만 DB 를 쓰고 아이템스카우트 토큰은 메모리·파일뿐이던 비대칭을 없앤다.
Vercel 은 인스턴스가 여러 개라 DB 가 유일한 공유처다. DB 저장 실패는 **던진다** —
삼키면 사용자는 "저장했다"고 믿는데 다른 인스턴스는 계속 옛 값을 쓴다.

소스에 상수로 박혀 있던 셀록홈즈 동반 쿠키(`_ga`, `sourcinglife_visitor_id`)도 금고로 옮겼다
(기본값은 이전과 동일, 환경변수나 DB 로 덮을 수 있음).

### D-6. HTTP 는 한 경로로 모은다 (`src/lib/crawl/fetch.ts`)

`crawlFetchJson` 이 헤더 프로필·타임아웃·재시도·응답 계약을 한 곳에서 정한다.

- 재시도: 429/5xx/네트워크/타임아웃만. **401/403 은 재시도하지 않는다** —
  만료된 자격증명으로 계속 두드리면 시간만 버리고 계정이 잠길 수 있다.
- 백오프: 지수 + 지터(±25%), `Retry-After` 존중(최대 30초)
- 세션 만료 시 금고 캐시를 비워, 사용자가 새 값을 넣자마자 반영되게 한다

**봇 탐지 회피의 한계를 명시한다.** 참조 구현은 `curl_cffi` 로 TLS 핑거프린트(JA3)까지
크롬으로 위장하지만, Node 에는 순수 JS 대응물이 없다(네이티브 바인딩 필요). 여기서 하는
일은 **HTTP 계층 신호를 일관되게 맞추는 것까지**다 — 브라우저와 같은 헤더 조합
(`sec-ch-ua`, `sec-fetch-*`, `Accept-Language`), 호스트에 맞는 Referer/Origin, 지터 섞은 재시도.
TLS 지문을 보는 방어에는 부족하며, 그런 벽을 만나면 브라우저 경로(`run-scrape.ts`)를 써야 한다.
공식 API(네이버·카카오)는 키로 인증하므로 `browserLike: false` 로 위장을 끈다.

### D-7. 실패는 타입 있는 사유로 구분한다 (`src/lib/crawl/errors.ts`)

`CrawlErrorCode` = `no_credential | session_expired | rate_limited | schema_mismatch |
contract_failed | network | timeout | upstream_error`

각 코드는 **사용자가 할 행동**과 **HTTP 상태**로 매핑된다. 매핑은 `Record<CrawlErrorCode, …>`
라서 코드를 추가하면 컴파일 에러가 난다.

**에러에 URL 을 담지 않는다.** 내부 API 는 토큰을 쿼리스트링에 싣기도 하고, 그러면 그 토큰이
로그·DB·HTTP 응답으로 그대로 샌다 (P-7). `source` + `endpoint` 라벨만 싣는다.

기존 `SellochomesError` 는 8곳이 `code === 'auth_expired'` 로 분기하므로 **공개 타입으로 유지**하고,
내부에서 `CrawlError` 를 번역해 넘긴다 (`schema_mismatch`, `rate_limited` 추가).

### D-8. 여러 소스를 묶을 때는 실패를 드러낸다 (`src/lib/crawl/report.ts`)

`runCrawlSources` 는 소스별로 `ok | empty | error | skipped` 를 기록한다.
**`empty` 는 성공이 아니다** — 호출은 됐는데 0건이면 확인이 필요하다는 뜻이다.
0건이 정상인 소스만 `emptyIsOk` 로 예외 처리한다. 못 채운 부분은 `gaps` 에 사람 말로 남고,
UI 는 이걸 그대로 ❓ (P-3) 로 띄우면 된다.

### D-9. 치유 결과는 자동 커밋하지 않는다

기준 파일 `src/lib/crawl/selectors.json` 은 **import 로 읽는다** (Vercel 읽기 전용 FS 에서도 확실).
치유로 바뀐 값은 `data/crawl-registry/selectors.local.json` 덮개에 쌓이고, 로드 시 병합된다.
확정은 사람이 기준 파일에 반영해 **커밋**한다 — 셀렉터 변경이 코드 리뷰 없이 배포되면 안 된다.

`data/crawl-registry/` 와 `data/crawl-snapshots/` 는 `.gitignore` 에 넣는다.
특히 스냅샷의 `page.html` 은 **로그인 상태 화면**이라 계정명·주문내역·토큰이 섞일 수 있다 (P-7).

## 결과

- 신규: `src/lib/crawl/` (types, contract, dom, registry, selectors.json, heal, export-package, vault, fetch, errors, report, page)
  - **배럴(`index.ts`)을 두지 않는다.** 하나로 묶으면 공통 fetch 만 필요한 곳까지
    금고(→`@/db`)와 cheerio 를 끌고 들어온다. 필요한 모듈을 직접 import 한다.
- 신규 CLI: `npm run crawl:list | crawl:history | crawl:revert | crawl:adopt`
- 신규 의존성: `cheerio` (+ 타입 참조용 `domhandler`)
- 새 실패 사유 `contract` → `/api/research/coupang-first-page/scrape` 가 **502** 로 응답
- `SellochomesError` 에 `schema_mismatch` · `rate_limited` 추가
- `fetchAllCategoryKeywords` 는 유지하되 완결 여부까지 주는 `harvestCategoryKeywords` 를 신설
- `loadKeywordPool` 은 파일이 없거나 깨졌으면 **던진다** (빈 풀 `keywords: []` 은 정상값)
- `DiscoverResult` 에 `sources` · `gaps` 추가 (기존 필드는 그대로) → `/vendors/discover` 화면에 ❓ 로 표시
- `/api/sellochomes` 응답에 `harvest` · `gaps` 추가 (절단된 수집을 완결처럼 내보내지 않는다)

### 계약을 느슨하게 잡은 자리와 그 이유

- **`minMatches` 는 1 로 둔다.** 처음엔 10 으로 잡았는데, 그러면 상품이 10개 미만인
  정상 키워드가 "사이트 구조 변경"(502)으로 오진된다. 판별력은 `attr`·`mustMatch`·
  `minTextLen` 이 담당한다 (예: `data-rank` 가 있고 그 값이 숫자여야 한다).
- **확장이 나중에 채우는 칸에는 fallback 을 두지 않는다.** `li.pv-month .num` 이 비었을 때
  `li.pv-month` 로 물러서면 라벨까지 포함한 셀 전체 텍스트가 값이 되어, 수집 종료 조건이
  오염된다. 추출 fallback 은 원래 코드에 있던 `상품명` 하나만 유지한다.
- **`sello.row_rocket` 은 무인 점검 대상이 아니다.** 로켓배송 상품이 하나도 없는 키워드에서
  0건이 정상이라, 이 항목의 계약 실패는 "깨짐"의 근거가 되지 못한다.
- **`minMatches` 만 있는 계약은 판별력이 없다.** 확장이 채우는 칸들이 여기 해당한다
  (초기엔 비어 있어 텍스트·숫자 제약을 걸 수 없다). 이 항목들은 휴리스틱 역추출이
  아예 동작하지 않으므로(정답을 특정할 수 없다) 잘못 치유될 위험은 없지만,
  `crawl:adopt` 로 사람이 넣은 후보는 느슨하게 통과할 수 있다 — 리뷰가 필요하다.

### 받아들인 비용

- **재시도가 기본 2회로 늘었다.** 예전에는 재시도가 아예 없었다. 조회성 호출뿐이라
  중복 부작용은 없지만, `keyword-caching` 폴링처럼 반복 호출되는 자리에서는
  최악의 경우 요청 수가 3배가 된다. 401/403 은 재시도하지 않으므로 계정 잠김 위험은 없다.
- **행 폴링이 매 주기 화면 전체를 읽는다.** 예전에는 페이지 안에서 개수만 셌다.
  대신 폴링과 최종 파싱이 **같은 결과**를 보게 됐다(예전에는 서로 다른
  `page.evaluate` 라 원리상 갈릴 수 있었다). 20행 기준 주기당 수백 밀리초로,
  기존 대기 예산(fast 30초 / full 180초) 안에 들어간다.

## 대안 검토

**(A) 셀렉터를 코드에 그대로 두고 테스트만 늘린다**
테스트는 "지금 맞다"만 알려 준다. 사이트가 바뀐 순간 프로덕션은 이미 0건을 수집하고 있고,
테스트는 다음 CI 때까지 그 사실을 모른다. 계약은 **런타임에** 판정한다.

**(B) 셀렉터를 DB 에 둔다**
셀렉터 변경은 코드 변경이다 — 리뷰와 롤백 이력이 있어야 한다. DB 에 두면 아무도 모르게 바뀐다.
git 이 이미 그 일을 한다.

**(C) 네트워크 페이로드를 캡처해 API 로 재생한다 (참조 구현의 `browser/replay.py`)**
가장 큰 이득이 될 수 있는 길이다 — 성공하면 3분짜리 스크랩이 초 단위가 되고 셀렉터 의존이
사라진다. 다만 셀록홈즈의 판매량·조회수는 **셀러라이프 확장이 쿠팡 wing API 를 불러 채우는**
값이라, 확장 없이 재생 가능한지 실측이 필요하다. 이번 범위에서는 제외하고 후속 ADR 로 남긴다.

**(D) TLS 핑거프린트 위장 라이브러리 도입**
네이티브 바인딩이 필요해 Vercel 배포와 충돌 위험이 크다. 현재 셀록홈즈는 헤더 수준으로
통과하고 있으므로 도입하지 않는다. 막히면 브라우저 경로가 이미 있다.

---

### D-10. 경로는 쓸 때마다 계산한다

`process.cwd()` 를 모듈 상수로 굳히지 않는다 (`registry.ts` / `export-package.ts` / `vault.ts`).

이건 이론이 아니라 실제로 사고가 난 지점이다. 연기 점검이 저장소를 건드리지 않으려고
임시 폴더로 cwd 를 옮겼는데, 경로가 import 시점에 이미 굳어 있어 **저장소의 레지스트리를
가짜 셀렉터(`div.list > div`)로 덮어썼다.** 그 상태로 실제 수집을 돌렸으면 전부 깨졌을 것이다.

`crawl:smoke` 는 셀록홈즈 계정 없이 돌아간다. 단위 테스트가 못 건드리는
Playwright 어댑터 경로(특히 `__name` 함정)를 여기서 잡는다.

**아직 못 한 것: 셀록홈즈 실제 화면과의 대조.** `selectors.json` 의 셀렉터가 진짜
DOM 과 맞는지는 로그인 세션 + 셀러라이프 확장이 있는 PC 에서
`npm run sello:scrape -- <키워드>` 를 돌려야 확정된다. 전제 조건은
`docs/CRAWL_REGISTRY.md` §10 에 정리해 두었다.
