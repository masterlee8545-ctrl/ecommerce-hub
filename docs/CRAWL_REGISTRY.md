# 크롤링 레지스트리 사용법 — "수집이 깨졌을 때 무엇을 하나"

> 근거: `docs/ADR-014.md`
> 코드: `src/lib/crawl/`
> 셀렉터 목록: `src/lib/crawl/selectors.json`

---

## 0. 세 줄 요약

1. 우리가 긁는 사이트(셀록홈즈, 아이템스카우트)는 **예고 없이 화면과 응답을 바꾼다.**
2. 그래서 "무엇이 맞는 결과인가"를 **계약(contract)** 으로 미리 적어 두고, 매 수집마다 확인한다.
3. 계약이 깨지면 프로그램이 스스로 4단계로 고쳐 보고, 못 고치면 **성공으로 기록하지 않는다.**

---

## 1. 용어 (처음 나오는 것만)

| 말 | 뜻 |
|---|---|
| **셀렉터 (selector)** | 웹페이지에서 원하는 부분을 집어내는 주소 (= 아파트 "3동 502호" 같은 것) |
| **계약 (contract)** | "이 셀렉터가 맞다"고 인정할 조건 (= 검수 기준서). 예: "최소 10건 잡혀야 하고, 각 항목에 순위 숫자가 있어야 한다" |
| **레지스트리 (registry)** | 셀렉터와 계약을 모아 둔 목록 파일 (= 주소록) |
| **치유 (heal)** | 셀렉터가 안 맞을 때 프로그램이 새 주소를 스스로 찾아보는 것 |
| **스냅샷 (snapshot)** | 깨진 순간의 화면을 통째로 저장한 것 (= 사고 현장 사진) |

---

## 2. 평소에는 아무것도 안 해도 된다

수집이 잘 되면 레지스트리는 조용히 있는다. 계약 확인은 수집할 때마다 자동으로 돈다.

지금 등록된 셀렉터를 보고 싶으면:

```bash
npm run crawl:list
```

---

## 3. 수집이 깨졌을 때

### 3-1. 어떻게 알게 되나

| 어디서 | 무엇이 보이나 |
|---|---|
| 화면(스크래핑 버튼) | "셀록홈즈 화면 구조가 바뀐 것으로 보입니다" |
| API 응답 | HTTP **502** + `reason: "contract"` |
| 워커/CLI 로그 | `[crawl] 행 계약 미충족 (…) — 치유 시도` |

> **502 를 쓰는 이유**: 우리 서버가 고장 난 게 아니라 **상대 사이트가 바뀐 것**이다.
> 500(우리 잘못)과 구분해야 "다시 눌러 보세요"가 아니라 "점검이 필요합니다"로 안내할 수 있다.

### 3-2. 프로그램이 먼저 해 보는 것 (자동, 순서대로)

```
1) 지금 쓰던 셀렉터        → 계약 통과하면 그대로 끝
2) 미리 등록해 둔 대안들    → 통과하는 게 있으면 그걸로 승격
3) 스스로 찾기(휴리스틱)    → 계약이 말하는 "정답" 을 화면에서 먼저 찾고,
                             배포마다 바뀌는 난수 이름(sc-…, css-…)은 버리고
                             data-testid·role 같은 안 바뀌는 표시로 새 주소를 조립.
                             조립한 걸 다시 계약으로 검증
4) 전부 실패               → 사고 현장 사진(스냅샷)만 남기고 멈춤
```

**3단계까지 성공하면 사람이 할 일이 없다.** 로그에 `치유 결과: healed/heuristic` 이 찍히고
바뀐 주소는 `data/crawl-registry/selectors.local.json` 에 쌓인다.

> ⚠ 3단계는 화면 한 장만 보고 판단한 것이라 **과적합** 가능성이 있다
> (= 그 화면에서만 우연히 맞을 수 있음). 이력에 `⚠샘플1건` 으로 표시된다.
> 다음 수집도 통과하는지 한 번 더 확인하는 편이 좋다.

### 3-3. 4단계까지 갔을 때 (사람이 할 일)

`data/crawl-snapshots/<셀렉터id>_<시각>/` 폴더가 생긴다. 안에는 두 파일이 있다.

- `page.html` — 깨진 순간의 화면 원본
- `PROMPT.md` — Claude 에게 물어볼 내용 (계약 조건까지 다 적혀 있음)

**순서:**

1. **`page.html` 을 한 번 훑어본다.**
   ⚠ 로그인한 상태의 화면이라 **계정명·주문내역·토큰이 섞여 있을 수 있다.**
   외부(claude.ai 등)에 올리기 전에 반드시 확인한다. 이 폴더는 git 에 올라가지 않는다.

2. 두 파일을 claude.ai 에 첨부하고 `PROMPT.md` 내용대로 물어본다.

3. 이런 모양의 답을 받는다:
   ```json
   { "candidates": ["ul.row[data-rank]", "div[data-testid='product-row']"] }
   ```

4. 그 답을 **그대로 믿지 않고** 저장된 스냅샷으로 다시 검증한다:
   ```bash
   npm run crawl:adopt -- sello.row data/crawl-snapshots/sello.row_2026-08-14T.../ '{"candidates":["…"]}'
   ```
   또는 답을 파일로 저장했다면 그 경로를 넘긴다.

   계약을 통과한 후보만 채택된다. **틀린 답을 받아도 레지스트리는 오염되지 않는다.**

5. 채택된 값을 `src/lib/crawl/selectors.json` 의 `primary` 에 반영하고 **커밋한다.**
   (덮개 파일은 로컬 전용이라 배포에는 안 올라간다. 셀렉터 변경은 코드 변경이므로
   리뷰를 거쳐야 한다.)

## 4. 되돌리기

치유가 잘못됐다 싶으면:

```bash
npm run crawl:history          # 무엇이 언제 어떻게 바뀌었나
npm run crawl:revert           # 가장 최근 변경 하나 되돌리기
npm run crawl:revert -- sello.row   # 특정 셀렉터의 최근 변경만
```

## 5. 셀렉터를 새로 추가할 때

`src/lib/crawl/selectors.json` 에 한 항목을 추가한다.

```jsonc
"sello.row_price": {
  "kind": "css",                    // 'css' = 화면 요소, 'json' = API 응답
  "primary": "li.price",            // 지금 쓸 주소
  "fallbacks": [],                  // 깨졌을 때 시도할 대안들
  "contract": { "minMatches": 10, "mustMatch": "\\d" },
  "within": "sello.row",            // 이 컨테이너 '안쪽' 기준이면 그 id, 아니면 null
  "description": "행의 판매가",
  "sampleUrls": [],
  "requiresBrowser": true,
  "healedAt": null,
  "healedFrom": null
}
```

**계약 쓰는 요령 — 이게 전부다.**

| 쓸 수 있는 조건 | 뜻 | 언제 쓰나 |
|---|---|---|
| `minMatches` | 최소 몇 건 잡혀야 하나 | 거의 항상 |
| `attr` | 이 속성이 **있어야** 인정 | 링크(`href`), 이미지(`src`), 데이터 속성 |
| `mustMatch` | 값이 이 정규식에 맞아야 함 | 도메인 확인, 숫자 확인, **버튼 글자 확인** |
| `minTextLen` | 글자가 이만큼은 있어야 함 | 제목·본문 |

- **`attr` 이나 `mustMatch` 나 `minTextLen` 중 하나는 넣어라.** 셋 다 없으면 3단계
  자동 찾기가 "정답"을 특정할 수 없어 대안 단계까지만 시도된다.
- **글자로 고르는 버튼도 계약으로 쓴다.** `primary: "button"` + `mustMatch: "^선택$"`.
  화면 문구가 바뀌면 코드가 아니라 이 파일만 고치면 된다.
- `kind` 가 `json` 이면 `status` 와 `jsonKeys` 만 쓸 수 있다 (`data.items` 같은 점 표기).
  CSS 계약 키를 섞어 쓰면 저장 시점에 걸린다.

새 항목을 넣으면 `src/lib/crawl/registry.test.ts` 가 자동으로 검사한다
(계약이 비었는지, `within` 이 실제로 있는지, id 형식이 맞는지).

## 6. 자격증명(쿠키·토큰)은 어디에 있나

전부 **금고** 하나를 지난다. 찾는 순서:

```
메모리(30초) → DB system_settings → 파일 .data/ → 환경변수
```

| 이름 | 무엇 | 환경변수 |
|---|---|---|
| `sellochomes_cookie` | 셀록홈즈 로그인 쿠키 (connect.sid) | `SELLOCHOMES_COOKIE` |
| `sellochomes_visitor_id` | 셀록홈즈 동반 쿠키 (없으면 쿠팡 응답 안 옴) | `SELLOCHOMES_VISITOR_ID` |
| `sellochomes_ga` | 셀록홈즈 동반 쿠키 | `SELLOCHOMES_GA` |
| `itemscout_token` | 아이템스카우트 토큰 (i_token) | `ITEMSCOUT_TOKEN` |

설정 화면에서 저장하면 **DB 에 들어간다.** Vercel 은 서버가 여러 대라 DB 만이 모든 서버가
같이 보는 곳이기 때문이다. (예전에는 아이템스카우트 토큰이 DB 에 안 들어가서, 저장해도
다른 서버에서는 안 보이는 문제가 있었다.)

⚠ 값은 **암호화 없이** 저장된다. 이 값을 읽을 수 있으면 그 계정에 그대로 접근할 수 있다.
로그나 에러 메시지에 값 자체를 절대 싣지 않는다.

## 7. 봇 탐지 회피는 어디까지 되나 (정직하게)

우리가 하는 것:
- 브라우저와 같은 헤더 조합 (`sec-ch-ua`, `sec-fetch-*`, `Accept-Language`)
- 호스트에 맞는 Referer/Origin
- 재시도 간격에 흔들림(지터)을 넣어 기계적인 주기를 없앰

**우리가 못 하는 것: TLS 지문 위장.**
참조한 파이썬 툴킷은 `curl_cffi` 로 통신 규격 수준의 지문까지 크롬으로 위장한다.
Node 에는 그에 직접 대응하는 순수 JS 수단이 없다. 그런 수준까지 보는 방어를 만나면
헤더만으로는 못 뚫는다 — 그때는 **진짜 브라우저를 띄우는 경로**
(`src/lib/sello-scraper/run-scrape.ts`) 를 써야 한다.

공식 API(네이버 검색, 카카오 로컬)는 키로 인증하므로 위장을 아예 끈다.

## 8. 실패 사유 읽는 법

| 코드 | 뜻 | 사용자가 할 일 | HTTP |
|---|---|---|---|
| `no_credential` | 쿠키/토큰이 없음 | 설정에서 입력 | 428 |
| `session_expired` | 로그인이 만료됨 | 설정에서 재발급 | 401 |
| `rate_limited` | 호출 한도 초과 | 잠시 후 다시 | 429 |
| `schema_mismatch` | 응답 구조가 바뀜 | 개발자 확인 | 502 |
| `contract_failed` | 화면 구조가 바뀜 | 이 문서 3장 | 502 |
| `network` / `timeout` | 연결 문제 | 잠시 후 다시 | 502 / 504 |
| `upstream_error` | 상대 서버 문제 | 잠시 후 다시 | 502 |

`session_expired` 는 **재시도하지 않는다.** 만료된 쿠키로 계속 두드리면 시간만 버리고
계정이 잠길 수 있다. 사람이 갱신해야 풀린다.

## 9. 명령 모음

```bash
npm run crawl:list        # 등록된 셀렉터와 계약 보기
npm run crawl:history     # 언제 무엇이 어떻게 바뀌었나
npm run crawl:revert      # 최근 변경 되돌리기 (여러 번 누르면 한 단계씩 더 거슬러 간다)
npm run crawl:adopt -- <셀렉터id> <스냅샷폴더> <응답파일|JSON>

npm run crawl:smoke       # 커널 통합 점검 (진짜 브라우저, 셀록홈즈 계정 불필요)
npm test -- src/lib/crawl # 커널 단위 테스트 (브라우저 불필요)

npm run sello:scrape -- <키워드>   # 실제 수집 (아래 전제 조건 필요)
```

## 10. 무엇을 어디까지 검증할 수 있나

| 명령 | 필요한 것 | 확인해 주는 것 |
|---|---|---|
| `npm test` | 없음 | 계약 판정·역추출 알고리즘·추출·리포트 |
| `npm run crawl:smoke` | Chrome | **Playwright 어댑터 경로 전체** — 화면 읽기 → 계약 → 클릭 → 추출 → 4단계 자동치유 |
| `npm run sello:scrape` | 아래 4가지 | 우리 셀렉터가 **셀록홈즈 실제 화면**과 맞는지 |

`crawl:smoke` 는 구조만 흉내 낸 가짜 화면을 씁니다. 네트워크에 나가지 않고, 레지스트리도
임시 폴더에만 씁니다 — 저장소의 셀렉터를 건드리지 않습니다.

### `sello:scrape` 전제 조건 (하나라도 없으면 못 돕니다)

1. **Windows + Chrome** (`process.platform === 'win32'` 체크가 있습니다)
2. **`.env.local` 의 `SELLO_EXTENSION_PATH`** — 셀러라이프 확장 압축해제 경로.
   그 폴더에 `manifest.json` 이 실제로 있어야 합니다
3. **셀러라이프 Chrome 확장 설치** — 판매량·조회수 칸을 채우는 주체입니다.
   없으면 화면에 "익스텐션 설치" 안내가 뜨고 수집이 중단됩니다
4. **`C:\sello-user-data` 프로필에 셀록홈즈 로그인** — 최초 1회 사람이 직접 로그인해야 합니다
   (구글/카카오 OAuth 라 자동화 불가)

추가로 **실행 전 모든 Chrome 창을 닫아야** 합니다 (프로필 락 충돌):
`taskkill //F //IM chrome.exe`
